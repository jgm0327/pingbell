# Pingbell 테스트 발송 이력 저장 정책

작성일: 2026-06-30

## 1. 현재 판단

테스트 발송 결과는 MVP 단계에서 `NotificationHistory`에 저장하지 않는다.

현재 테스트 발송은 사용자가 알림 채널 설정이 유효한지 즉시 확인하기 위한 검증 기능이다. 반면 `NotificationHistory`는 incident open / resolved 알림의 발송 상태, 자동 재시도, 수동 재전송을 추적하는 운영 이력이다.

두 이력을 같은 테이블과 화면에 섞으면 사용자는 실제 장애 알림 실패와 단순 설정 검증 실패를 혼동할 수 있다. 따라서 MVP에서는 테스트 발송 결과를 화면의 즉시 성공/실패 메시지로만 표시하고, 운영 알림 이력과 재시도 정책에는 연결하지 않는다.

## 2. 결정 이유

- `NotificationHistory`는 현재 `incident_id`가 필수인 구조다.
- `NotificationHistoryResponse`도 incident, monitor, notification type을 전제로 한다.
- 테스트 발송은 특정 incident 없이 실행되므로 기존 모델에 넣으려면 nullable incident 또는 별도 category가 필요하다.
- 테스트 발송 실패를 `FAILED` 이력으로 저장하면 자동 재시도나 수동 재전송 후보처럼 보일 수 있다.
- 운영 장애 알림 이력 화면에는 실제 장애 대응에 필요한 발송 이력만 남기는 편이 사용자에게 명확하다.

## 3. 현재 표시 정책

테스트 발송 결과는 알림 채널 설정 화면에서만 즉시 표시한다.

- 성공: 테스트 발송 성공 메시지를 표시한다.
- 실패: sender가 반환한 실패 메시지를 표시한다.
- 비활성 채널: 테스트 발송을 차단한다.
- 다른 사용자의 채널: 기존 소유자 조회 조건으로 차단한다.

알림 이력 화면에는 테스트 발송 결과를 표시하지 않는다.

## 4. 데이터 모델 영향

이번 정책에서는 DB schema를 변경하지 않는다.

변경하지 않는 항목:

- `NotificationHistory.incident_id nullable` 전환
- `NotificationType.TEST_SEND` 추가
- `NotificationHistory` category/source 필드 추가
- 테스트 발송 전용 history table 추가
- 테스트 발송 재시도 상태 추가

## 5. 운영상 한계

테스트 발송 결과를 저장하지 않으므로 다음 정보는 장기 조회할 수 없다.

- 과거 테스트 발송 성공/실패 이력
- 테스트 발송 실패 원인의 시간별 변화
- 누가 언제 테스트 발송을 눌렀는지에 대한 감사 로그

이 한계는 MVP 단계에서 허용한다. 현재 목적은 알림 채널 설정의 즉시 검증이며, 감사 로그나 장기 검증 이력은 아직 핵심 기능이 아니다.

## 6. 추후 저장이 필요해지는 조건

다음 요구가 생기면 별도 이슈로 테스트 발송 이력 저장을 재검토한다.

- 팀 단위 운영에서 누가 테스트 발송을 실행했는지 감사 로그가 필요하다.
- 고객 지원을 위해 과거 테스트 발송 실패 원인을 조회해야 한다.
- 알림 채널 품질을 지표로 집계해야 한다.
- 테스트 발송과 운영 발송을 별도 탭 또는 별도 화면으로 구분할 UX가 필요하다.

이 경우 `NotificationHistory`를 그대로 재사용하기보다 `NotificationDeliveryAttempt`처럼 incident 없는 발송 시도를 표현할 수 있는 별도 모델을 먼저 검토한다.

## 7. Backend / Frontend 작업 분해

현재 정책 기준으로 추가 구현은 하지 않는다.

완료된 상태:

- Backend 테스트 발송 API는 `NotificationHistory`를 만들지 않는다.
- Frontend는 알림 채널 설정 화면에서 테스트 발송 결과를 즉시 표시한다.
- 알림 이력 화면은 incident 기반 운영 알림 이력만 표시한다.

후속 개선 후보:

- 알림 채널 목록에서 enabled / disabled 필터 제공
- 테스트 발송 실패 메시지의 민감 정보 마스킹 점검
- 테스트 발송 성공/실패 메시지 UX 개선

## 8. 테스트 기준

문서 작업이므로 자동 테스트는 없다.

정책이 코드와 맞는지 확인할 때는 다음을 본다.

- `NotificationChannelTestSendService`가 `NotificationHistory`를 저장하지 않는다.
- `NotificationHistory`의 `incident`는 필수 관계로 유지된다.
- 알림 이력 조회 화면에는 테스트 발송 이력이 표시되지 않는다.

## 9. 포트폴리오에 남길 포인트

- 운영 장애 알림 이력과 설정 검증용 테스트 발송을 분리해 사용자가 실제 장애 대응 이력만 추적할 수 있게 했다.
- 테스트 발송은 sender 구현을 재사용하지만, incident 기반 이력과 재시도 정책에는 연결하지 않아 도메인 의미가 섞이지 않게 했다.
- MVP에서는 감사 로그보다 즉시 검증 UX를 우선하고, 장기 이력 저장은 실제 운영 요구가 생긴 뒤 별도 모델로 확장하도록 결정했다.
